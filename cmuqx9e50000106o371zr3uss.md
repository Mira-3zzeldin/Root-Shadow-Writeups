> This article explores one of the most fundamental ideas in security: why green tests mean nothing against a purposeful failure, illustrated through real threat-modeling findings from my graduation project, InstaShield.

## How Can This Be Abused?

By the time InstaShield's core payment logic was passing every test I threw at it, I thought I understood the system. Login worked. Payments confirmed. Biometric checks matched the right proof to the right user, the way Part I described. On paper, nothing was broken.

Functionally correct and adversarially safe turned out to be two different claims, and nothing in a passing test suite tells you which one you actually have. The difference was the attack surface: every place where the system accepted input, made a decision, or trusted another component.

* * *

## A different question entirely

"Does it work?" is a question about intended use. You give the system valid input, in the expected order, from a well-behaved caller, and you check whether the output is correct. Almost all software gets evaluated this way, because almost all testing assumes the person on the other end is trying to use the system, not break it.

STRIDE — Microsoft's threat-modeling framework for Spoofing, Tampering, Repudiation, Information Disclosure, Denial of Service, and Elevation of Privilege — asks a structurally different question of the same code: not "what is this supposed to do," but "what happens if an actor is not who or what I assumed?" It doesn't require finding a clever new attack. Most of the time it just requires taking the system's own logic seriously enough to ask what happens when an assumption embedded in it turns out to be false.

The clearest example of that difference showed up in something as unglamorous as JWT verification.

* * *

## Spoofing: the token gets to choose how it's checked

The original verification call looked like ordinary, working code:

```javascript
jwt.verify(token, secret);
```

It worked. Valid tokens signed with the expected secret passed. Invalid ones failed. By the "does it work" standard, there was nothing to fix.

The STRIDE question was different: what is this code actually trusting, and who controls it? A JWT carries its signing algorithm inside its own header — `alg: HS256`, `alg: RS256`, or other algorithm choices. If the verification call doesn't explicitly restrict accepted algorithms, the verifier risks trusting an algorithm choice controlled by the token itself, including insecure configurations the application was never intended to accept. The token, not the server, was quietly choosing the rules it would be judged by.

The fix was one argument:

```javascript
jwt.verify(token, secret, { algorithms: ['HS256'] });
```

That single restriction closed the assessed attack path, reducing its project risk evaluation from CVSS 9.1 to 0.0. Nothing about the "happy path" changed. Every legitimate token still verified exactly as before. The only thing that changed was what the server was willing to accept as a legitimate question in the first place.

That's the pattern STRIDE exists to catch: code that is correct for every input you expected, and silent about every input you didn't.

The same question appeared in the biometric flow from Part I. The issue was never whether the biometric service could produce a correct result — it was whether an attacker could create a believable result without going through the process that was supposed to produce it.

* * *

## Elevation of Privilege: when "it looks enforced" isn't the same as "it is enforced"

The suspended-account check was, if anything, a harder case to catch, because reading the code gave every impression that it worked.

```javascript
if (user.suspended) {
    throw new ForbiddenError();
}
```

The condition is correct. The logic is correct. The problem was one layer removed from the condition itself: the `suspended` field was never actually persisted when an account was suspended elsewhere in the system. The check was real, but the data it depended on was never being written, so `user.suspended` silently evaluated to a falsy default on every request, for every account, regardless of status. A suspended account and an active account looked identical to this check, because the flag that was supposed to distinguish them had quietly stopped existing in practice.

"Does it work?" had no way to catch this, because from a functional standpoint, active accounts behaved correctly — which was the only case anyone was routinely testing. The STRIDE question *what happens to an account that shouldn't have access, and can I confirm that path is actually blocked, not just apparently blocked?* ... is what surfaces a gap like this, because it forces you to test the case the system was supposedly designed to stop, not just the case it was designed to allow.

* * *

## Information Disclosure: the leak that isn't in the response body

Some of the more interesting cases in InstaShield weren't about data leaking through a response, they were about data leaking through *behavior*.

Authentication is one example. If a login attempt for a non-existent user fails fast, while a login attempt for a real user with a wrong password takes measurably longer — because a real bcrypt comparison ran in one case and didn't in the other — an attacker doesn't need the response body to say "user not found." The response *time* already said it. InstaShield closes that channel by running a bcrypt comparison against a dummy hash even when the user doesn't exist, so the timing profile of "wrong password" and "no such account" stays effectively the same.

Payment intents raise a related but distinct version of the same question. When a user requests a payment intent that belongs to someone else, what should the server say? A `403 Forbidden` may be technically correct, depending on the application's resource exposure policy — but it can also confirm that the requested resource exists, which is itself information the requester wasn't entitled to. InstaShield returns `404` instead, treating "not yours" and "doesn't exist" as indistinguishable from the requester's point of view. Neither of these is a case of data being exposed somewhere it shouldn't be. Both are cases where a *pattern* in the system's own honesty was the thing worth protecting.

* * *

## Business Logic Abuse: when valid features become attack paths

The most counterintuitive category, and the one "does it work" is least equipped to catch, is abuse of features that are working exactly as designed.

Self-transfers are a good example. Nothing about letting a user send money to their own account is a bug — it's arguably a reasonable feature. The problem only appears once you ask what else that capability enables: repeated self-transfers can be used to manufacture transaction activity, which, depending on how velocity-based fraud detection is designed, may distort the signals used for risk evaluation. The transfer logic doesn't need a flaw for this to work. It needs an absence of the question "what does this let someone do that has nothing to do with its intended purpose?" InstaShield blocks self-transfers specifically to close that path, not because transferring to yourself is inherently dangerous, but because of what it enables downstream.

Numeric input validation follows the same logic from the ledger side. Rejecting `NaN`, `Infinity`, and negative amounts before they reach financial calculations isn't defending against a clever exploit — it's defending against the fact that "the field accepts a number" and "the field only accepts numbers that make sense in a ledger" are two different guarantees, and only one of them was actually being enforced.

* * *

## The principle underneath all of it

None of these cases were found by someone being unusually clever. They were found by asking a structurally different question of code that, in every case, already looked like it worked. STRIDE doesn't generate new vulnerabilities out of nowhere — it gives you a systematic way to ask "how could this specific piece of logic be abused" for each category of actor and each category of harm, instead of relying on a vulnerability happening to look wrong on inspection.

That's a meaningfully different posture than debugging. Debugging asks why something failed. Threat modeling asks what would have to be true for something to *succeed* at doing the wrong thing — and then checks whether that condition is currently possible. The JWT check wasn't failing. The suspended-account check wasn't failing. Both were succeeding, completely, at a task that wasn't the one anyone thought they were performing.

Once I started treating "it works" as the beginning of the question rather than the end of it, a new problem became unavoidable: threat modeling tells you what *could* go wrong before it happens. It doesn't tell you which of those risks are worth designing around from the start, and which ones are acceptable to leave as calculated trade-offs. That's a different kind of decision — one that has to be made deliberately, before the code exists, rather than discovered afterward.
